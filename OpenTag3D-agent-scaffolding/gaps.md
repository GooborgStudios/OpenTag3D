# Scaffolding gaps (out of scope for the first AGENTS.md pass)

Things noticed while researching the repo that would help agents (and human contributors) but aren't being tackled yet. Tracked here so they don't get lost, and so we can decide deliberately whether/when each becomes its own follow-up PR against OpenTag3D.

- **No CONTRIBUTING.md.** No documented PR process, branch naming, or review expectations beyond what CI enforces (build + format). Would help clarify things like: who merges supporter-list PRs, whether spec.json changes need consortium sign-off before a PR is even opened, etc. Deliberately not guessed at for the first `AGENTS.md` pass, since the repo owner doesn't yet know the maintainer's unwritten house style; this project's own PR (opened by a first-time contributor) is meant to surface that firsthand and could feed a follow-up `CONTRIBUTING.md` project.
- **No link between GitHub activity and the consortium's proposal→vote process.** Full findings in [notes-spec-maintenance-workflow.md](notes-spec-maintenance-workflow.md) §3. `about.md` documents a two-tier voting-member/non-voting-member governance model for spec changes, but nothing in the repo (no issue template, no label, no log) ties a merged PR to an actual vote — as far as the checkout can show, voting (if it happens) happens off-repo in Discord with no artifact left in git. Worth asking the maintainer directly how this is meant to work before proposing a template/log to formalize it.
- **No release automation, and no drift check between the places a version bump touches.** Full findings in [notes-spec-maintenance-workflow.md](notes-spec-maintenance-workflow.md) §2. A version bump is: hand-edit `_data/spec.json`'s `version` field, hand-add a changelog entry to the bottom of `spec.md`, and manually push a bare (unannotated) git tag — nothing checks the three agree, and a major bump additionally requires manually freezing a new `assets/json/spec_v{N}.json` snapshot before the fields change (nothing checks that happened either). Related: `index.md`'s `announcement:` front-matter string (e.g. announcing v2.0) is a fourth manually-edited, version-linked spot with no tie to the release process — nothing prompts updating or retiring it on the next bump (see [notes-automation-opportunities.md](notes-automation-opportunities.md) §1). A `workflow_dispatch` "cut a release" job could do all of this atomically, but that's a build-it-or-not question for the maintainer, not something to add speculatively.
- **Merge-rights/review process for non-owner contributors is unconfirmed.** `notes-spec-maintenance-workflow.md` §1 found no merge commits and an almost entirely single-author recent commit log (plus dependabot) — consistent with squash-merges by the repo owner, but branch protection lives in GitHub settings, not the checkout, so this can't be fully confirmed from the repo alone. Ask rather than assume if this matters for a given task.
- **No automated tests for `opentag3d.js`.** The byte-level encode/decode/NDEF-packing logic (spec field parsing, NTAG page dumps, Flipper/Proxmark3/NFC-Tools import/export) has no unit tests — correctness currently rests on manual browser verification. Even a handful of pure-function tests (encode → decode round-trip per field type) would catch regressions cheaply, since none of that logic touches the DOM or Web NFC.
- **No CODE_OF_CONDUCT.md** or explicit license-header/contribution norms beyond the repo-level `LICENSE` (GPLv3).
- **No architecture note for `make.html`/`read.html`.** Both are large (~700-1000 line) single-file pages mixing inline `<style>`, form-generation-from-spec JS, and imports from `opentag3d.js`/`site.js`. The draft AGENTS.md covers the shared modules but not how the page-local form-building code works; worth a deeper note if agents start editing those pages often.
- **Windows dev-server story is undocumented beyond "unsupported."** Deliberately left out of the draft AGENTS.md body (that file should describe the repo, not any one contributor's machine) — but if this keeps coming up, it may be worth a short doc on a WSL-based workaround, or confirming `bundle exec jekyll build` (no SSL, no serve) is sufficient for most content changes.
- **No schema/structural validation for `_data/spec.json`.** Full findings in [notes-spec-json-extensibility.md](notes-spec-json-extensibility.md). CI (`bundle exec jekyll build`) only fails on invalid JSON or a broken Liquid template — it doesn't catch a bogus `type` string (silently undecoded, no error), overlapping `core` field byte ranges, or a field that overruns the `0x00`–`0xDF` address range. A lightweight Node validation script (checking `type` against the enum `opentag3d.js` actually implements, range overlaps, address-range bounds, `id` uniqueness, and that `required`/`added` are present and well-formed) would close this cheaply and could run in `format.yml` or a new CI job.
- **No round-trip tests tying `_data/spec.json` to `opentag3d.js`.** Related to the existing "no automated tests for `opentag3d.js`" item above, but specifically: every `core` field already ships `examples` — running each through `encodeFieldValue` → `decodeTagBuffer` and asserting the decoded value matches would be a cheap first unit-test suite with no DOM/Web NFC dependency.
- **Remaining `core` byte budget is undocumented and unenforced.** Only 24 of 224 bytes are unused across 4 gaps (largest: 13 bytes) as of spec v2.003 — see notes-spec-json-extensibility.md §3. Nothing computes or surfaces this, so a contributor proposing a new on-tag field has to manually re-derive the byte map to find free space. Worth a small script/CI annotation if new `core` fields keep coming up.
- **`getting-started.md`'s three supporter tables duplicate `_data/supporters.yml` by hand.** Full findings in [notes-automation-opportunities.md](notes-automation-opportunities.md) §2/§4. The "Supported Printers," "Supported Filament Brands," and mobile-app tables are hand-typed Markdown that already overlap real entries in `supporters.yml` (NFC Tools, SpoolSense, SpoolFlux, Polar Filament appear in both, tracked separately). Generating these tables via Liquid from `supporters.yml` (extending its schema with the extra columns getting-started.md needs) would remove an active drift risk — this is the single highest-value item this pass found.
- **No link-checking in CI.** Dozens of outbound links across `getting-started.md`, `about.md`, and `articles/` (Discord, third-party vendor sites, GitHub PRs/repos) are never verified; a dead link only surfaces when a user reports it. A `lychee`/`markdown-link-check` job (scheduled or on PR) would close this cheaply.
- **Prettier's format check excludes Markdown.** `format.yml` globs `**/*.{js,scss,json,yml,yaml}` — the site's most-edited file type (`.md`) has no formatting check at all.
- **No article index or feed, and inconsistent article front matter.** `articles/` posts have no `date`/`tags` front matter and nothing enumerates them automatically (new posts are linked by hand, e.g. from the homepage announcement banner); `_config.yml` has `atom_feed: { hide: true }` explicitly disabling the theme's feed support. Fine at 2 posts; worth revisiting if this becomes a recurring channel. See notes-automation-opportunities.md §3.
- **Supporter intake stops short of full automation.** The GitHub issue template ([.github/ISSUE_TEMPLATE/support.yml](.github/ISSUE_TEMPLATE/support.yml)) collects structured fields that map almost 1:1 onto `_data/supporters.yml`, but a maintainer still hand-transcribes each issue into YAML. No equivalent intake template exists for community printer mods/firmware (invited in prose on `index.md`) or for reporting third-party apps missing from getting-started.md. See notes-automation-opportunities.md §4/§5.
- **No CI/CD staging environment or post-deploy check.** `pages.yml` deploys straight to production (`main`) on every push with no PR preview and no post-deploy smoke test/internal-link crawl. See notes-automation-opportunities.md §5.
- **No content-level tests for cross-references in `_data/*.yml`.** Nothing asserts every `_data/supporters.yml` entry's `logo` file actually exists, that `_data/navigation.yml`'s links resolve to real pages, or that `category`/`implstage` values stay within the enums declared at the top of `supporters.yml`. A small script would be cheap and would have caught the getting-started.md/supporters.yml drift (above) going forward, once that refactor lands. See notes-automation-opportunities.md §5.
- **No bridge between GitHub activity and Discord.** New supporters, releases, and articles currently get announced (if at all) by hand; a GitHub Actions → Discord webhook step on release/merge-to-main would close this without needing a bot. See notes-automation-opportunities.md §5.
